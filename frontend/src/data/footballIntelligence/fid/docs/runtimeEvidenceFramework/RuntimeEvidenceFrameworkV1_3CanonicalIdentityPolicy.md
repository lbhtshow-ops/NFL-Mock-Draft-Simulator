# REF-V1.3 Canonical Identity Policy

REF V1 uses two deliberately separate profiles. `EXACT_ARTIFACT_BYTES` hashes a supplied `Uint8Array` byte-for-byte without parsing, text conversion, path binding, or normalization. `STRUCTURED_REF_DECLARATION` validates one of the seven REF contracts, removes only governed derived/self-referential fields, wraps the declaration in a versioned domain-separation envelope, canonicalizes it, converts it to UTF-8, and hashes it.

The structured input domain is JSON-like, behavior-free data: strings, finite numbers other than negative zero, booleans, null, dense arrays, and own enumerable data properties of plain objects with `Object.prototype` or null prototypes. Object keys are sorted by JavaScript code-unit order. Array order is always preserved because no V1.2 field declares set canonicalization semantics; uniqueness validation does not imply order insensitivity. Empty arrays and objects remain distinct. Strings are preserved exactly with JSON escaping: Unicode normalization is not performed, so precomposed and decomposed text remain distinct. UTF-8 uses `TextEncoder`. Numbers use the ECMAScript JSON number representation after rejecting non-finite values and negative zero.

Undefined, functions, symbols, BigInt, Date, Map, Set, sparse arrays, circular structures, inherited/custom prototypes, accessors, symbol keys, non-finite numbers, negative zero, and non-byte artifact inputs are rejected. Sensitive fields are rejected rather than silently redacted. Prohibited examples include credentials, passwords, access/refresh tokens, API/private keys, connection strings, authorization headers, cookies, unrestricted environment dumps, and raw role graphs. Extensions are identity-bearing and remain subject to V1.2 extension and sensitive-data validation.

For all seven contracts, every own declaration field is identity-bearing except `validation`, `contentIdentity`, `derivedContentIdentity`, `calculatedDigest`, and `verificationStatus`. `validation` and verification results are derived metadata. Digest/identity fields are excluded solely to avoid recursive identity. Contract type, contract version, schema version, contract mode, lifecycle, timestamps or temporal references, reference fields, observation/review/supersession fields, redaction/custody/integrity declarations, extensions, and ordered arrays are identity-bearing. Volatility is not an exclusion reason.

The domain envelope binds `LBHT:REF:STRUCTURED_DECLARATION`, canonicalization version, contract type, contract version, schema version, and canonical content. SHA-256 is provided by Web Crypto and encoded as exactly 64 uppercase hexadecimal characters. Comparisons are exact and case-sensitive. A well-formed or matching digest proves only a local calculation over supplied bytes/content; it does not prove authorization, authenticity, external receipt, external execution, target identity, operational success, or truth.

Errors distinguish invalid declarations, unsupported values, executable properties, sensitive fields, circular references, ambiguous arrays/numbers, invalid digests, mismatch results, unsupported contracts, and unavailable SHA-256 providers. Digest mismatch is an identity-verification result, never a governed-operation failure.

Future controller use is documented only: obtain exact bytes; calculate byte identity; validate declarations; derive structured identities; compare expected identities; record observations; then independently evaluate authorization and preconditions. This sprint implements none of the controller, filesystem, submission, authorization, database, persistence, or execution behavior.
